# Data Engineering Translation Dictionary

> ⚠️ **Черновик.** Словарь собран без вычитки редактором-терминологом: применяй как справочник, при расхождении с каноном (`translation-glossary.md` → «Общая таблица») и с готовыми словарями выигрывают они. Спорные ряды помечены «проверить» в комментарии.

Словарь для переводчиков технических статей по инженерии данных: конвейеры, озёра и хранилища, потоковая обработка, форматы и табличные форматы, оркестрация, качество и управление данными. **Не догма** — отражает узус русскоязычного сообщества дата-инженеров (Хабр, документация облачных провайдеров, переводы книг O'Reilly) на 2026 год. Если автор оригинала использует устоявшийся в его команде вариант, и он не противоречит словарю — оставляй авторский.

**Границы словаря.** Термины СУБД (репликация, шардирование, транзакции, индексы, оптимизатор запросов, OLAP/OLTP) — в `databases-translation-dictionary`; датасет, признаки, feature store, ноутбуки — в `ml-ai-translation-dictionary`; Kubernetes-объекты и планирование подов — в `k8s-translation-dictionary`; CI/CD, staging-окружения, GitOps — в `devops-translation-dictionary`. Здесь их нет намеренно: при совместной активации бери вариант из профильного словаря.

## Принципы

1. **Имена проектов и продуктов — оригинал, не склоняются.** `Spark`, `Kafka`, `Airflow`, `Flink`, `Iceberg`, `Delta Lake`, `Hudi`, `Trino`, `dbt` — как в документации; `dbt` всегда строчными, включая начало предложения (перестрой фразу, если пунктуация не позволяет). «В Кафке», «на Спарке» — только в разговорном регистре, в статьях — «в Kafka», «на Spark».
2. **Русское слово по умолчанию.** `data lake` → «озеро данных», `data warehouse` → «хранилище данных», `stream processing` → «потоковая обработка», `data quality` → «качество данных». Англицизм первым — только там, где он реально узус техтекста: «топик», «брокер», «партиция», «консьюмер».
3. **Составные с pipeline.** Одиночный `pipeline` по канону — «конвейер»: `data pipeline` → «конвейер данных». «Дата-пайплайн», «ETL-пайплайн» — допустимы как составные в техтексте, один вариант на текст.
4. **Аббревиатуры — оригинал.** ETL, ELT, DWH, CDC, DAG, SCD, DLQ, UDF, AQE, HDFS. При первом упоминании допустимо раскрыть сокращение рядом с ним — «CDC (Change Data Capture)»: это расшифровка аббревиатуры, а не толкование термина.
5. **Термины без устоявшегося русского варианта — оригинал со сноской.** `backfill`, `backpressure`, `watermark`, `lakehouse`, `data mesh`, `tombstone` — в тексте `backfill[^1]`, в конце материала `[^1]: Backfill — повторный прогон конвейера за прошлые периоды для дозагрузки или пересчёта данных. — Прим. перев.` Дальше — термин без сноски. Три исхода для любого термина: русское слово, оригинал, оригинал со сноской.
6. **Имена API, поля конфигов, SQL-ключевые слова — как в коде.** `spark.sql.shuffle.partitions`, `MERGE INTO`, `schedule_interval`, `{{ ref('stg_orders') }}` — в backtick, не переводятся и не склоняются. Комментарии в коде переводятся, идентификаторы — нет.
7. **Медальонные слои — русскими прилагательными, цвет латиницей — в именах схем.** «Бронзовый / серебряный / золотой слой» в нарративе; `bronze`, `silver`, `gold` — только как имена схем и папок в коде.

## Раздел 14. Падежные формы (для частых терминов)

### Topic → топик

| Падеж | Форма |
|-------|-------|
| Именительный | топик |
| Родительный | топика |
| Дательный | топику |
| Винительный | топик |
| Творительный | топиком |
| Предложный | топике |
| Мн.ч. им. | топики |
| Мн.ч. род. | топиков |

### Consumer / producer → консьюмер / продюсер

Склоняются как существительные мужского рода: консьюмера, консьюмеру, консьюмером; продюсера, продюсеру, продюсером. Мн.ч.: консьюмеры / продюсеры, консьюмеров / продюсеров. Если выбран вариант «потребитель / производитель» — то же, но по всему тексту.

### Partition → партиция

Женский род: партиции, партицию, партицией, в партиции. Мн.ч.: партиции, партиций. «Партиция» и «секция» — один вариант на текст (databases-словарь).

### Data lake / DWH → озеро данных / хранилище данных

Склоняется первое слово: «в озере данных», «из хранилища данных», «к хранилищу данных». Аббревиатура DWH не склоняется: «в DWH», «из DWH».

### Spark, Kafka, Airflow, Flink, Iceberg, Hudi, Trino, dbt

**Не склоняются**: «в Kafka», «на Spark», «в Airflow», «таблицы Iceberg». Разговорные «в Кафке», «на Спарке», «в Эйрфлоу» — не для статей. Род — мужской для Spark, Flink, Airflow, Trino, Iceberg, Hudi («Spark запустил»), женский для Kafka («Kafka приняла») — по узусу Хабра; проверить.

### DAG

Не склоняется: «запуск DAG», «несколько DAG», «в этом DAG». Род — мужской. Транслитерация «даг» — разговорно.

## Раздел 15. Типовые ошибки переводчика статей по инженерии данных

### 1. Перевод имён проектов и API

```
✗ «Загрузите данные в Айсберг-таблицу»
✓ «Загрузите данные в Iceberg-таблицу»

✗ «Создайте датафрейм и вызовите метод "перепартиционировать"»
✓ «Создайте DataFrame и вызовите `repartition()`»
```

### 2. Смешение регистров для producer / consumer / offset

В одном тексте — один вариант:

```
✗ Продюсер пишет в топик, потребитель читает по смещению, а консьюмер-группа держит офсет.
✓ Продюсер пишет в топик, консьюмер читает по офсету, а группа консьюмеров хранит офсет.
```

### 3. Склонение несклоняемых

```
✗ «В Кафке 12 партиций»            →  ✓ «В Kafka 12 партиций»
✗ «Запустите DAG'и через Эйрфлоу»  →  ✓ «Запустите DAG через Airflow»
✗ «Dbt собирает витрины»            →  ✓ «Витрины собирает dbt» (dbt всегда строчными)
```

### 4. Перевод полей конфигов и SQL

Ключи параметров, имена моделей и SQL-ключевые слова — **никогда** не переводи:

```python
spark.conf.set("spark.sql.shuffle.partitions", 200)   # НЕ «партиции.перетасовки»
```

```sql
MERGE INTO gold.orders t USING silver.orders s ON t.id = s.id   -- НЕ «СЛИТЬ В золото.заказы»
```

### 5. Калька «pipeline → пайплайн» вне составных

```
✗ «Пайплайн падает на шаге загрузки»
✓ «Конвейер падает на шаге загрузки» / «ETL-пайплайн падает на шаге загрузки»
```

### 6. Определение термина инлайн вместо сноски

```
✗ «Мы запускаем backfill (повторный прогон за прошлые даты) раз в неделю»
✓ «Мы запускаем backfill[^3] раз в неделю»
   [^3]: Backfill — повторный прогон конвейера за прошлые периоды для дозагрузки или пересчёта данных. — Прим. перев.
```

### 7. Путаница измерений и размерностей

```
✗ «Таблица размерностей клиентов»   (dimension table)
✓ «Таблица измерений клиентов»
```

### 8. Калька «является» и «позволяет»

```
✗ «Iceberg является табличным форматом, который позволяет делать time travel»
✓ «Iceberg — табличный формат с поддержкой time travel»
```

### 9. Пассив без необходимости

```
✗ «Данные могут быть загружены в бронзовый слой инкрементально»
✓ «Данные загружаются в бронзовый слой инкрементально» / «В бронзовый слой данные можно грузить инкрементально»
```

### 10. Смешение каталогов

`Iceberg catalog` (каталог табличного формата: REST, Hive, Nessie) и `data catalog` (каталог данных для людей: DataHub, OpenMetadata) — разные понятия. В переводе держи разграничение явно: «каталог Iceberg» и «каталог данных».

- [ ] **Медальонные слои** — «бронзовый / серебряный / золотой слой» в нарративе, `bronze` / `silver` / `gold` — только в коде

- [ ] **dimension** — «измерение» в моделировании, не «размерность»
- [ ] **Каталоги** — «каталог Iceberg» и «каталог данных» не смешаны

- [ ] **Калек избегли** — нет «является», «позволяет», «осуществляет», «производит»
- [ ] **Кавычки** — «ёлочки», внутри — „лапки“; схемы «звезда» и «снежинка» — в ёлочках
- [ ] **Числа** — `10 000` (пробел), `3,14` (запятая), `5 ГБ`, `100 мс`

## Раздел 17. Когда термин имеет несколько устоявшихся переводов

Если в русскоязычном сообществе дата-инженеров нет единого варианта (`consumer` → «консьюмер» / «потребитель», `offset` → «офсет» / «смещение», `checkpoint` → «чекпоинт» / «контрольная точка»), действуй по приоритету:

1. **Смотри на оригинал.** Если автор пишет разговорно и опирается на жаргон, сохраняй такой же уровень формальности в переводе.
2. **Смотри на площадку.** Хабр и инженерные блоги — чаще «консьюмер», «офсет», «чекпоинт». Документация провайдеров и формальные тексты — «потребитель», «смещение», «контрольная точка».
3. **Если переводишь в первый раз — бери канонический (первый) вариант словаря.** Для рядов с пометкой «проверить» первый вариант — рабочая гипотеза черновика, а не решение редактора.
4. **В одном тексте — один вариант.** Это правило важнее любого «правильного» выбора.

## Раздел 18. Что делать с новыми терминами

Если в статье встречается термин, которого нет в этом словаре:

1. **Проверь профильные словари** — `databases-`, `ml-ai-`, `k8s-`, `devops-translation-dictionary`: термин может принадлежать соседнему домену.
2. **Проверь русскую документацию облачных провайдеров** по Managed Kafka / Spark / Airflow — там переводы прошли редактуру.
3. **Проверь русские издания книг O'Reilly** («Основы инженерии данных», «Высоконагруженные приложения» Клеппмана) и хаб «Big Data» на Хабре.
4. Если нигде нет — оставь **в оригинале**; если термин узкий, при первом упоминании дай сноску переводчика: `Термин[^N]` + `[^N]: Термин — что это. — Прим. перев.` Помета «устоявшегося перевода нет» — в отчёт проверяльщику, не в текст.
5. Не придумывай свой перевод — это вносит непоследовательность в экосистему.

Все новые термины, которые встретились в работе, проверяльщик (`translation-verifier`) может предложить добавить в словарь. Решение о добавлении — за оркестратором и редактором-терминологом; до вычитки словарь остаётся в статусе `draft`.
