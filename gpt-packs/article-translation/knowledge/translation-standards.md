# Стандарты перевода

Правила перевода технических статей с английского на русский. Действуют для всех субагентов модуля `article-translation-agent`. Модуль рассчитан на **английский оригинал**; параметр языка остаётся в интерфейсе, но словари, каталог калек и правила типографики покрывают только EN → RU (ревью 2026-09-17: заявленный ранее немецкий не имел ни одного словарного термина и ни одной DE-специфичной нормы — заявление снято, чтобы не обещать то, чего нет).

## Принцип блочного соответствия (action на всех этапах)

**Главное правило всего pipeline.** Перевод, редактура и проверка идут **строго по блокам оригинала**. Один блок оригинала → один блок перевода в той же позиции. Свои изменения в структуру не вносить — даже когда после идёт адаптация под площадку (она выполняется отдельным шагом доработки оркестратора, а не внутри субагентов).

### Что такое «блок»

Блок — это единица структуры markdown, разделённая пустыми строками. Типы блоков:

| Тип блока | Пример | Правило |
|-----------|--------|---------|
| Заголовок | `# H1`, `## H2`, `### H3`; setext `Title` + `====`/`----` | Уровень сохраняется один-к-одному (H2 → H2, не H1 и не H3); setext-заголовок в переводе — ATX того же уровня |
| Абзац | обычный текст | Один абзац оригинала → один абзац перевода |
| Список | `- item` / `1. item` | Количество и порядок пунктов — байт-в-байт |
| Вложенный список | `  - subitem` | Уровень вложенности сохраняется |
| Блок кода | ```` ```...``` ```` | Целиком как есть, переводятся только строки-комментарии внутри |
| Inline code | `` `code` `` | Не трогать |
| Изображение | `![alt](url)`, `<img src>`, `<figure>/<figcaption>` | URL не трогать, переводится только `alt`, `title` и подпись (caption) |
| Цитата | `> quote` | Один блок цитаты → один блок цитаты |
| Admonition | `> **Note**`, `> [!WARNING]` | Тип admonition сохраняется; ключевое слово (Note / Warning / Tip) переводится по узусу площадки: «Примечание», «Внимание», «Совет» |
| Таблица | `\| col \|`, HTML `<table>` | Структура (число строк и колонок) сохраняется; заголовки колонок переводятся; код и числа в ячейках — как в блоке кода |
| Сноска | `[^N]` | Авторские — номер и позиция один-к-одному, содержимое переводится. Плюс **сноски переводчика** — единственное санкционированное добавление блоков, см. раздел «Санкционированные добавления» |
| Разделитель | `---` | Сохраняется на той же позиции |
| HTML-вставка | `<details>`, `<summary>` | Теги не трогать, текст внутри переводить |
| Встраивание | `<iframe>`, YouTube-embed, tweet, `<video>` | Переносится как есть, на той же позиции; подпись переводится |
| Task-list | `- [ ] item` | Как список: число и порядок пунктов, чекбоксы сохраняются |
| Формула | `$…$`, `$$…$$` | Не трогать |
| HTML-комментарий | `<!-- … -->` | Переносится как есть (это не контент) |

**Что блоком не является** (и в счётчик не входит): навигация сайта, «Related posts», cookie-баннеры, формы подписки, комментарии читателей, «Originally published at…», био автора вне статьи, дата-обновления вида «Update 2025-01-…» вне тела статьи. Оркестратор вырезает это **до** блочного скана (санитайзинг источника, `subagent-protocol.md` → «Санитайзинг источника»); если это осталось в оригинале, переданном стадиям, — это дефект загрузки, а не перевода.

### Что запрещено на всех этапах

- ❌ **Объединять блоки** — два абзаца оригинала нельзя склеивать в один
- ❌ **Дробить блоки** — один абзац оригинала нельзя разбивать на два (даже если он длинный)
- ❌ **Переставлять блоки** — порядок строго как в оригинале
- ❌ **Удалять блоки** — даже если кажется лишним
- ❌ **Добавлять блоки** — никаких «введений от переводчика», «выводов от редактора», «связок между абзацами». Единственное исключение — сноски переводчика (см. «Санкционированные добавления»)
- ❌ **Менять тип блока** — список нельзя превратить в абзац, цитату — в обычный текст и наоборот
- ❌ **Менять уровень заголовка** — H2 остаётся H2
- ❌ **Терять изображения** — каждый `![alt](url)` оригинала должен присутствовать в переводе на той же позиции

### Что разрешено внутри блока

Внутри одного блока абзаца переводчик и редактор могут:
- Подбирать русские конструкции, отличающиеся от английского порядка слов
- Менять пассив на актив (только редактор, не переводчик)
- Переставлять придаточные внутри одного предложения
- Объединять или разбивать **предложения внутри одного абзаца** (только редактор; переводчик — предложение за предложением)

Структурный контракт «блок-к-блоку» при этом сохраняется: количество абзацев, списков, заголовков, кода, картинок и сносок в переводе — равно количеству в оригинале.

### Машинная сверка блочного контракта

Счётчики блоков, код, картинки, ссылки, числа и сноски **считает не модель, а скрипт** «check_translation_fidelity» (внутренняя автопроверка репозитория, в чате недоступна — проверь этот пункт вручную) (ревью 2026-09-17: самоотчёт проверяльщика пропустил расхождения в трети переводов библиотеки). В backend — action `validate_translation_fidelity` с `on_error: block` перед проверяльщиком; на нативном пути оркестратор гоняет скрипт после каждой стадии и вкладывает его таблицу в промт проверяльщика. Блокирующие коды: потерянный лид, заголовки по уровням, число и содержимое блоков кода (без комментариев), картинки (URL и порядок), таблицы, авторские сноски, сноска переводчика без пометки, длинное тире в переводе оригинала без тире (`EM_DASH_ADDED`, раздел «Тире и дефисы»). Абзацы, пункты списков, цитаты, разделители, ссылки, числа — предупреждения: проверяльщик разбирает их по смыслу (локализация дат и единиц легитимно меняет числа; якоря оглавления — ссылки). Стадии счётчики в отчётах **не приводят** — они приходят из скрипта; стадия описывает, где именно разошлось и почему.

### Лид (вступление до первого H2)

Частая ошибка при загрузке статьи — обрезание текста между заголовком H1 и первым подзаголовком H2. Это **лид** (вступление, intro, abstract): один или несколько абзацев, иногда с картинкой/цитатой/списком, которые автор поставил до структурной разбивки.

**Лид — такой же контент, как и остальной текст.** Никаких исключений:

- Оркестратор при загрузке источника **обязан** захватить весь текст от H1 до конца статьи, включая всё между H1 и первым H2.
- Если из URL пришёл markdown без лида (только H2-секции) — это сбой парсинга. Оркестратор должен повторить загрузку (или попросить пользователя вставить полный текст) и убедиться, что лид присутствует.
- Если в загруженном тексте **нет H1** (заголовок пришёл в метаданных, тело начинается с абзацев или с H2) — оркестратор ставит H1 из заголовка статьи первой строкой; лид — блоки до первого H2. Статья без H2 вовсе — лид не выделяется, счётчик считает всё тело.
- Переводчик переводит лид как обычные блоки (абзацы / списки / картинки), сохраняя порядок и тип.
- Редактор работает с лидом по тем же правилам блок-к-блоку.
- Скрипт сверки считает блоки до первого H2 отдельной строкой; потерянный лид — блокирующий код `LEAD_LOST`.

### Адаптация под площадку — отдельный шаг

Если пользователь после готового перевода выбирает «адаптировать под Хабр / VC.ru / Telegram» — это **не задача субагентов pipeline**. Это отдельный шаг доработки оркестратора через `content-editor` (или `write-social-post` для Telegram-резюме). Структуру переводу при адаптации можно менять, но только после полного прохождения pipeline и явного выбора пользователя. После адаптации проверяльщик прогоняется повторно **в режиме без блочного контракта** (`block_contract: off`): сверяет числа, код, картинки, ссылки, термины и факты, но не счётчики абзацев (`subagent-protocol.md` → «Площадочная адаптация»). Адаптированный файл сохраняется двойником `{stem}-{площадка}.md` (например `-habr.md`) рядом с каноническим переводом.

### Изображения

Изображения — частый случай потери при переводе. Правило строгое:

- Каждый `![alt](url)` оригинала → ровно один `![alt-перевод](url)` в переводе, на той же позиции относительно соседних блоков
- URL картинки **не трогать** — оставлять байт-в-байт, даже если ссылка ведёт на CDN автора оригинала. Локальная копия картинки («images» (внутренний материал системы, в эту выгрузку не входит)) — решение шага сохранения/публикации (Хабр требует habrastorage), не стадий: стадии работают с оригинальным URL
- `alt`-текст переводить (он попадает в a11y и поиск)
- Подпись под картинкой (caption — отдельный абзац или `*курсив*` сразу под картинкой) переводить как обычный абзац
- Если картинка содержит текст (схема, диаграмма с подписями) — текст внутри **не перерисовывать**; в подпись добавить перевод ключевых надписей в формате «На схеме: … — …» (санкционированное добавление внутри блока подписи, см. ниже)
- HTML-картинки (`<img src="...">`) — атрибут `src` не трогать, переводить только `alt=""` и `title=""`

Скрипт сверки сравнивает упорядоченный список URL картинок; любое расхождение — блокирующее.

### Санкционированные добавления — честный список

Правило «структуру не трогать» имеет ровно четыре исключения. Всё остальное — галлюцинация.

| # | Что | Где | Кто | Как отличить машинно |
|---|-----|-----|-----|----------------------|
| 1 | **Сноски переводчика** (единственное добавление БЛОКОВ) | маркер `[^N]` при первом упоминании, определение в блоке сносок после авторских | переводчик (этап 1); редактор — только по маркеру `MISSING_FOOTNOTE` из брифинга или словаря | текст сноски заканчивается `— Прим. перев.` |
| 2 | **Перевод надписей на схеме** в подписи к картинке | внутри блока подписи, формат «На схеме: …» | переводчик | внутри блока подписи, блоков не добавляет |
| 3 | **Уточнение относительной даты** | в скобках после выражения: «в прошлом году (2025)», «на момент написания (март 2026)» — год/месяц из даты публикации оригинала | переводчик | число появляется в переводе; скрипт сверки покажет `NUMBERS_ADDED`, проверяльщик подтверждает по дате оригинала |
| 4 | **Блок атрибуции** в конце перевода | после финального `---`, канон ниже | переводчик | скрипт сверки его не считает (служебный хвост) |

Расшифровка аббревиатуры при первом упоминании — «mTLS (mutual TLS)» — добавлением не считается: это часть перевода термина (см. «Пояснения — только сноской»).

### Сноски переводчика

Пояснения узкоспециализированных терминов оформляются **сносками переводчика** `[^N]` (политика и тест распространённости — `translation-glossary.md`). Контракт:

- **Кто добавляет:** переводчик на этапе 1 (по тесту распространённости / брифингу). Редактор на этапе 2 сноски **не сочиняет**: у него нет оригинала, и определение «своими словами» — источник фактических галлюцинаций (ревью 2026-09-17). Редактор переносит описание из скобок в сноску (текст уже есть), снимает сноску у whitelist-термина, переносит на первое упоминание; пропущенную сноску узкого термина он помечает маркером `🔁 MISSING_FOOTNOTE` — текст добавляет оркестратор из брифинга/словаря или переводчик повторным кругом.
- **Нумерация** продолжает авторские сноски оригинала (авторские `[^1]`-`[^4]` → переводческие с `[^5]`). Номера авторских сносок не сдвигаются. В посекционном режиме оркестратор передаёт стадии «последний использованный номер» (`subagent-protocol.md` → «Посекционный режим»).
- **Маркировка:** текст каждой сноски переводчика заканчивается пометкой `— Прим. перев.` — по ней сноски машинно отличимы от авторских (скрипт сверки: сноска без пометки, которой нет в оригинале, — блокирующий код `TRANSLATOR_FOOTNOTE_UNMARKED`).
- **Позиция:** маркер — при первом упоминании термина в тексте; определения — в общем блоке сносок в конце, после авторских. Где сноску не ставить: заголовки H1-H3 (ставь на первое упоминание в тексте под заголовком), код, ссылки, URL, alt-тексты. Если первое упоминание термина — в подписи к картинке или в пункте списка, сноска ставится там же: подпись и пункт — обычные текстовые блоки.
- **Прослеживаемость:** переводчик перечисляет добавленные сноски (номер → термин) в служебной сводке после атрибуции; редактор — в отчёте.

Все остальные добавления блоков по-прежнему запрещены.

### Пояснения переводчика — только сноской

Одна политика для всех видов пояснений (ревью 2026-09-17 сняло три конкурирующих: инлайн-заметку `[прим. перев.: …]`, сноску и «оригинал в скобках»):

| Что нужно пояснить | Как |
|--------------------|-----|
| Узкий термин, малоизвестный продукт | сноска-определение при первом упоминании, `— Прим. перев.` |
| Шутка, идиома, культурная отсылка, которую буквальный перевод теряет | буквальный перевод в тексте + сноска «Игра слов: … — Прим. перев.» |
| Опечатка или фактическая ошибка в оригинале | текст переводится **как есть**, сноска «В оригинале …; вероятно, имеется в виду … — Прим. перев.». Исправлять автора в тексте нельзя |
| Whitelist-термин в нетипичном значении | оригинал термина в тексте + сноска с пояснением значения в статье |
| Полезная русская версия ресурса по ссылке (kubernetes.io/ru, MDN ru) | URL в тексте не меняется; сноска «Русская версия: … — Прим. перев.» |
| Устаревшая версия в оригинале (статья старше 12 месяцев, вышли новые релизы) | сноска при первом упоминании версии: «На момент перевода актуальна версия X. — Прим. перев.» — **только** если версия подтверждена (брифинг ресёрчера или проверка оркестратора); без подтверждения сноска не ставится |
| Расшифровка аббревиатуры | не сноска: «mTLS (mutual TLS)» при первом упоминании в тексте, ставит переводчик (или по брифингу); редактор проверяет, что расшифровка одна и на первом упоминании |

Инлайн-заметки `[прим. перев.: …]` в прозе **упразднены**: скрипт сверки не отличает их от текста, проверяльщик считал их галлюцинацией. Скобки в прозе допустимы ровно в двух случаях — введение и расшифровка аббревиатуры (`translation-glossary.md` → «Пояснения — только сноской»).

## Принцип литерализма (этап 1: переводчик)

Первый этап — **дословный перевод**, а не пересказ. Задача переводчика — сохранить структуру и смысл оригинала максимально близко к тексту. Стилевая полировка — задача редактора на следующем этапе.

### Что переводить дословно

- Заголовки и подзаголовки — структуру и порядок не менять. Заголовок статьи переводится буквально; SEO-заголовок и TL;DR для площадки — артефакты шага адаптации, не перевода.
- Предложения — переводить по одному, без объединения и дробления.
- Метафоры и аналогии автора — сохранять, не заменять русскими аналогами на этапе перевода.
- Шутки и культурные отсылки — переводить буквально; пояснение, если без контекста непонятно, — сноской (таблица выше), не в скобках.
- Списки — структуру и порядок пунктов сохранять.
- **Голос автора.** Лицо и число сохраняются: «I» → «я», «we» → «мы» (это «мы» автора и его команды, не переводчика и не издателя — редактор не подменяет его на «мы» компании-публикатора). Обращение к читателю: «you» в объяснении → «вы» (строчная, `brand-terminology`), «you» в шаге инструкции → императив («настройте», «запустите») допускается редактором. Род автора для глаголов прошедшего времени («я заметила») — по подписи, местоимениям в оригинале или профилю автора; если род установить нельзя — конструкции без рода («мне удалось заметить»), не угадывать.

### Что НЕ переводить

| Элемент | Действие |
|---------|----------|
| Блоки кода (```` ```...``` ````) | Оставлять как есть. Перевести **только** строки-комментарии внутри (`# comment`, `// comment`, `<!-- comment -->`). Строковые литералы (`print("Connecting…")`, тексты ошибок в коде, `echo "…"`) — **не переводить**: они часть кода. Примеры вывода команд (`$ kubectl … ` и то, что напечатала команда) — не переводить. |
| Однострочный код в `<code>` / backticks | Не переводить. |
| Конфигурационные файлы (YAML, JSON, TOML, ini) | Ключи и значения не трогать. Перевести только комментарии. |
| Команды shell, имена файлов, пути | Не переводить (`kubectl get pods`, `/etc/hosts`). |
| Названия продуктов, технологий, проектов | Оставлять оригинал: Kubernetes, Docker, PostgreSQL, Cilium, eBPF, Helm. Малоизвестный продукт, важный для статьи, — пояснить сноской переводчика при первом упоминании (`translation-glossary.md` → тест распространённости). |
| Имена и фамилии авторов, спикеров | Транслитерация только если автор сам так подписывается на русском. Иначе — оригинал. Имена в латинице не склоняются: «статья Lin Sun», «по словам Brian Grant». |
| Названия компаний | Оригинал: Google, Microsoft, Anthropic. Исключения — компании с устоявшимися русскими названиями. Латинские названия в кавычки не берутся. |
| Аббревиатуры (API, CPU, GPU, DNS, TLS, RBAC) | Оригинал. Узкую аббревиатуру при первом упоминании расшифровать в скобках («mTLS (mutual TLS)»); определение, если нужно, — сноской переводчика. Общеизвестные (API, CPU, GPU, RAM, JSON, HTML, HTTP, URL, SQL) — без расшифровки. |
| URL, ссылки, идентификаторы | Не менять. **Текст ссылки** `[text](url)` переводится как обычный текст; URL — нет. Относительные ссылки и якоря (`/docs/…`, `#section`) сохраняются как есть, даже если якорь ведёт на английский заголовок, — оркестратор отмечает их в отчёте как «требуют проверки при публикации». |
| Сноски `[^N]` и их содержимое | Авторские: сохранять номера и атрибуции один-к-одному. Сноски переводчика — добавлять по контракту раздела «Сноски переводчика». |
| Изображения, диаграммы | Оставлять `![alt](url)` как есть. Перевести `alt`-текст и подпись под изображением. |
| Лицензия, копирайт, дисклеймеры автора | Переводятся как текст, если стоят внутри статьи; правовой статус перевода — в блоке атрибуции (см. «Права на перевод»). |

### Перевод комментариев в коде

```python
# Connect to the database          →    # Подключаемся к базе данных
def connect():                     →    def connect():
    conn = psycopg2.connect(...)   →        conn = psycopg2.connect(...)
    return conn  # returns Connection  →    return conn  # возвращает Connection
```

Имена переменных, функций, методов — НЕ переводятся. Скрипт сверки сравнивает код без строк-комментариев байт-в-байт: перевод комментария — норма, любое другое изменение — блокирующий код `CODE_CHANGED`.

> **Терминология, приоритеты и доступность словарей** вынесены в `translation-glossary.md` (доставляется тем же стадиям).

## Структурные элементы

### Заголовок статьи

Переводи буквально. SEO-заголовок, TL;DR, мета-описание и хабы — артефакты шага адаптации под площадку (`subagent-protocol.md` → «Площадочная адаптация»), не перевода и не редактуры.

### Кавычки

| В оригинале | В переводе |
|-------------|-----------|
| "double" | «ёлочки» (русский стандарт) |
| 'single' | «ёлочки» или курсив, если внутри `«...»` |
| `code` | `code` без изменений |
| “smart quotes” | «ёлочки» |

Внутри уже открытых ёлочек — использовать „лапки“. Латинские названия продуктов и компаний в кавычки не берутся.

### Тире и дефисы

| Английский | Русский |
|------------|---------|
| em-dash (—) | длинное тире (—) с пробелами |
| en-dash (–) в диапазонах | короткое тире (–) без пробелов: 2020–2024 |
| hyphen (-) | дефис в составных словах |

**Безусловное правило: нет тире в оригинале — нет длинного тире в переводе.** Если в исходном тексте нет ни одного тире-знака препинания (em-dash `—`, а также набранных вместо него ` – ` и ` -- ` с пробелами), в переводе **ноль** длинных тире: в прозе, заголовках, списках, таблицах, цитатах и тексте сносок переводчика. Исключений по стилю, ритму, плотности или «так звучит естественнее» нет; там, где по-русски просится тире, ставят двоеточие, запятую, точку (два предложения) или скобки по `technical-punctuation.md`. Это касается и грамматического тире между подлежащим и сказуемым, которое редстандарт вендора называет обязательным («Kubernetes — стандарт оркестрации»): в переводе без тире в оригинале фразу перестраивают («Kubernetes стал стандартом оркестрации», «Kubernetes представляет собой…»), а не ставят тире (решение 2026-09-24). Правило действует на всех стадиях: переводчик тире не вводит, редактор не добавляет, проверяльщик и площадочная адаптация (`content-editor`) тоже. Вне правила только служебные элементы с фиксированным каноном: подпись сноски `— Прим. перев.`, блок атрибуции, код и инлайн-код, URL. Короткое тире в диапазонах `2020–2024` и дефисы правило не затрагивает. Гейт: `check_translation_fidelity`, блокирующий код `EM_DASH_ADDED` (после переводчика и после редактора, `on_error: block`).

**Плотность длинных тире: только по оригиналу, потолок — по редстандарту.** Длинное тире (—) появляется в переводе **лишь там, где em-dash стоял в исходном тексте** — это перенос, не привнесение. Переводчик и редактор **не добавляют** длинные тире, которых в оригинале не было (ради ритма, вместо двоеточия/запятой/точки, в присоединительных конструкциях). Обратное тоже верно: если в оригинале тире несёт функцию (определение, вставная конструкция), его сохраняют. Приоритет при конфликте: норматив `brand-terminology.md` (≤ 2 на 1 000 знаков, блокирующий потолок 3,5) действует и для перевода; если плотность тире оригинала выше потолка, редактор заменяет **сначала** привнесённые тире, затем — авторские вставные конструкции на двоеточие/запятую/скобки по `technical-punctuation.md`, не трогая числа, диапазоны `2024–2026` и ссылки. Формулировка «длинное тире в предложениях по умолчанию» — ошибка, её в правилах модуля больше нет.

### Числа и единицы измерения

- Разрядность: `10,000` → `10 000` (неразрывный пробел). `1.5K` / `10M` в прозе → `1,5 тыс.` / `10 млн`.
- Десятичный разделитель: `3.14` → `3,14` (запятая).
- Единицы: `5 GB` → `5 ГБ`, `5 GiB` → `5 ГиБ` (двоичные приставки не сводить к десятичным), `100 ms` → `100 мс`, `2 GHz` → `2 ГГц`, `req/s` / `RPS` → `запросов в секунду` (при повторах допустим «RPS»), `QPS` → «запросов в секунду».
- Проценты: `50%` → `50 %` по редстандарту (неразрывный пробел), если `brand-terminology` не задаёт иное для площадки.
- Валюта: `$100` → `100 $`, `€100` → `100 €`, `$2.3M` → `2,3 млн $`. Один вариант на весь текст; словами («долларов») — только если так в оригинале.
- `billion` → «миллиард», `trillion` → «триллион».
- Имперские единицы (`mi`, `ft`, `lb`, `°F`) в техстатье редки: переводятся в метрические с исходным значением в скобках («100 миль (161 км)») — единственный случай, когда в скобках допустимо число; скрипт сверки покажет `NUMBERS_ADDED`, проверяльщик подтверждает пересчёт.
- Время: 12-часовой формат → 24-часовой («3 pm» → «15:00»); часовой пояс сохраняется как в оригинале («15:00 PST»), не пересчитывается.
- `Q3 2024` → «III квартал 2024 года»; `FY2025` → «2025 финансовый год».

### Даты

- `January 15, 2026` → `15 января 2026 года`.
- `01/15/2026` → `15 января 2026 года` (US-формат: месяц/день/год).
- `2026-01-15` (ISO) → `15 января 2026 года` в прозе; в коде, таблицах и метаданных ISO остаётся.
- **Относительные даты** («last year», «this spring», «as of writing», «recently») переводятся буквально, а год/месяц берётся из даты публикации оригинала и добавляется в скобках: «в прошлом году (2025)» (санкционированное добавление № 3). Дата перевода для этого не используется.

### Буква ё

В переводе — последовательно с «ё» (редстандарт вендора — `redstandard_skill` в «brand» (внутренний материал системы, в эту выгрузку не входит)): «ещё», «всё», «идёт». Смешение «е/ё» по тексту проверяльщик отмечает как дефект единообразия.

> **Каталог калек и протокол правки редактора** вынесены в `translation-calques.md` (доставляется редактору и проверяльщику).

## Принципы редактора (этап 2)

Редактор работает с дословным переводом и адаптирует его под нормы русского языка и инфостиль **строго в границах одного блока**. Не объединяет, не дробит и не переставляет блоки (см. «Принцип блочного соответствия» выше — это главное правило).

**На этом этапе** допускаются и приветствуются (внутри одного блока):

- Разбиение длинных **предложений** (английский часто длиннее) — но в пределах одного абзаца, без выноса в новый абзац.
- Перестройка порядка слов внутри предложения под русский синтаксис.
- Замена неудачных калек на нормальный русский.
- Удаление избыточных вводных конструкций («It is important to note that…») — без удаления самого предложения.
- Замена пассивного залога на активный, где действие важнее агента; пассив сохраняется там, где он смысловой.
- Адаптация идиом: если буквальный перевод звучит чужеродно, а смысл ясен из контекста — функциональный русский эквивалент; если смысл держится на игре слов — оставить буквальный перевод и сноску переводчика (она уже стоит с этапа 1; нет — маркер `🔁 MISSING_FOOTNOTE`).
- Унификация терминологии по «Общей таблице терминов» (`translation-glossary.md`), активным словарям и брифингу `terminology-researcher` (если был): один термин — одно написание по всему тексту.
- Проверка единичности расшифровки аббревиатуры (одна, на первом упоминании).
- Приведение пояснений терминов к политике сносок: перенос описания из скобок в сноску переводчика, удаление «обратного перевода» в скобках после русского термина, снятие сноски у whitelist-термина.

**На этом этапе НЕ допускаются:**

- **Объединение или дробление блоков** — два абзаца в один или один в два (контракт блок-к-блоку).
- Перестановка блоков, изменение типа блока, изменение уровня заголовка.
- Сокращение или удаление содержательных абзацев.
- Изменение примеров кода или конфигов — даже комментариев (их перевёл переводчик).
- Изменение чисел, дат, имён, ссылок.
- Добавление фактов и утверждений, которых не было у автора.
- **Сочинение определений терминов** и «возврат оригинала» по догадке: у редактора нет оригинала, восстановить исходный термин из русской «отсебятины» он может только угадав. Русский вариант вне whitelist/брифинга редактор **помечает** (`🔁 EDITOR_RESHAPE`, причина «термин вне whitelist»), а не «возвращает оригинал».
- Своих выводов, оценок, связок «как видно из вышеизложенного».
- Подмена «мы» автора на «мы» компании-публикатора.
- Адаптация под площадку (Хабр / VC.ru / Telegram) — это отдельный шаг доработки оркестратора.

Если редактор считает, что какой-то блок принципиально требует переработки, — он помечает блок маркером и оставляет комментарий. Маркеры редактора (все — в отчёте редактора, **не в тексте перевода**, чтобы не уйти проверяльщику как галлюцинация):

| Маркер | Когда | Кто разбирает |
|--------|-------|---------------|
| `🔁 EDITOR_RESHAPE` | блок нельзя поправить без обращения к оригиналу: бессмысленная калька, вероятная ошибка перевода, термин вне whitelist | оркестратор: повторный круг переводчика по указанным блокам |
| `🔁 MISSING_FOOTNOTE` | узкий термин без сноски при первом упоминании, текста сноски у редактора нет | оркестратор: текст из брифинга/словаря, иначе переводчик |
| `⚠️ FEEDBACK-UP` | дефект выше по конвейеру: похоже, пропущен абзац, потеряна картинка, лид не переведён («stage-isolation» (внутренний материал системы, в эту выгрузку не входит)) | оркестратор: сверка со скриптом, повторный круг стадии-источника |

## Принципы проверяльщика (этап 3)

Проверяльщик сравнивает финальный перевод с оригиналом. На входе у него — таблица машинной сверки (`fidelity_report`): счётчики блоков, лид, код, картинки, ссылки, числа, сноски уже посчитаны. Он **не пересчитывает** их заново, а:

1. **Разбирает сигналы машинной сверки по смыслу 📐** — для каждого блокирующего кода находит конкретный потерянный / склеенный / разбитый блок и цитирует его; для предупреждений (абзацы, ссылки, числа) решает, дефект это или легитимная локализация (дата, единица, якорь оглавления), и говорит, что именно.
2. **Галлюцинации 🚨:** утверждения в переводе, которых нет в оригинале.
3. **Пропуски ❗:** факты, цифры, имена, ссылки, предложения из оригинала, которые отсутствуют в переводе.
4. **Искажения смысла ⚠️:** перевод, который меняет логику автора (особенно отрицания, модальность, условия, причинно-следственные связи).
5. **Терминологические ошибки 🔤:** нарушения политики трёх исходов (с учётом брифинга `terminology-researcher`, если был): «отсебятина» вне whitelist, непереведённый whitelist-термин, узкий термин без сноски при первом упоминании, пояснение в скобках вместо сноски, «обратный перевод» в скобках, пояснение не на первом упоминании, сноска без пометки.
6. **Несоответствие чисел/дат/имён 🔢:** любое расхождение по фактам сверх легитимной локализации.
7. **Изменения в коде 💻:** любая правка строк кода, кроме комментариев (машинный код `CODE_CHANGED` он подтверждает цитатой).
8. **Остаточные кальки 🪞 (информативно):** до 10 примеров, без правок — сигнал оркестратору о качестве редактуры; в итоговую сумму расхождений не входят.

Проверяльщик **не** оценивает стиль и читаемость — это задача редактора. Его выход — отчёт с маркерами по типам нарушений, вердиктом и блоком машинных правок `corrections` (`structured-corrections`).

### Вердикт и что с ним делает оркестратор

| Вердикт | Условие | Действие оркестратора |
|---------|---------|-----------------------|
| ✅ соответствует | ни одного блокирующего сигнала сверки, 0 галлюцинаций, 0 искажений, 0 расхождений в цифрах/коде | показать результат |
| ⚠️ публиковать с правками | только точечные правки (`corrections` с уникальным `find`) | применить правки (все / выборочно), мини-сверка изменённых блоков |
| 🚨 ручной пересмотр | потерян лид, потеряны блоки/картинки, галлюцинация в целый абзац, склейка/дробление абзацев, изменён код | **повторный круг стадии-источника** (`subagent-protocol.md` → «Ветка провала»), не «применить правки» |

### Режим без блочного контракта

После площадочной адаптации оркестратор запускает проверяльщика с флагом `block_contract: off`: счётчики блоков, лид, разделители и абзацы **не проверяются** (структуру адаптация меняет легитимно), проверяются код, картинки, ссылки, числа, термины, галлюцинации и искажения. Скрипт сверки в этом режиме — advisory.

> **Протокол обновления словаря (этап 0)** вынесен в `translation-dictionary-update.md` (доставляется terminology-researcher).

## Контекст по терминам (пример секции брифинга terminology-researcher)

Формат секции «Контекст по терминам» терминологического брифинга (полный контракт брифинга — `translation-dictionary-update.md`):

```markdown
### eBPF
> Первое употребление: «We use eBPF to monitor syscalls.»
Комментарий: общеупотребительная аббревиатура в Linux-сообществе, перевод не используется.

### sidecar
> Первое употребление: «A sidecar container handles authentication.»
Комментарий: устоявшийся термин в русскоязычной K8s-документации, склоняется через дефис.
```

Брифинг передаётся всем трём субагентам pipeline через промт оркестратора. Переводчик опирается на колонки `handling` (translate / original / footnote), `russian` (инлайн-вариант) и `footnote_text`, редактор — на них же при унификации и сверке сносок, проверяльщик — на `handling` и `familiarity` при поиске терминологических ошибок.

## Атрибуция и frontmatter перевода

Единственный канон блока атрибуции (три формата, жившие в переводчике, оркестраторе и реальных файлах, сведены в один; ревью 2026-09-17). Блок — служебный хвост после финального `---`, в блочный счётчик не входит:

```markdown
---

*Перевод с английского. Оригинал: [{Title}]({URL}) — {Author}, {площадка}, {YYYY-MM-DD}. {Права: по лицензии CC BY 4.0 | с разрешения автора | права уточняются}. Перевод: {переводчик / редакция}, {YYYY-MM-DD}. Сноски с пометкой «Прим. перев.» добавлены при переводе.*
```

Frontmatter сохранённого перевода (канон, проверяет «fix_content_frontmatter» (внутренняя автопроверка репозитория, в чате недоступна — проверь этот пункт вручную)):

```yaml
---
title: "{заголовок перевода}"
type: translation
original_title: "{Title}"
author: "{Author}"
source_url: "{URL}"
source_language: en
original_date: {YYYY-MM-DD}
translated_date: {YYYY-MM-DD}
stage: final            # literal | edited | final | adapted
status: draft           # draft | ready | published
platform: null          # habr | vc | null — у двойника адаптации
rights: unknown         # license:<id> | permission | unknown
literal: «date-slug» (внутренний материал системы, в эту выгрузку не входит)
```

## Права на перевод

Перевод — производное произведение. На шаге загрузки оркестратор фиксирует правовой статус (`rights`): лицензия оригинала (CC BY / CC BY-SA / Apache docs / …), разрешение автора (переписка, дата) или «неизвестно». Поле пишется во frontmatter, в блок атрибуции и в реестр; при `unknown` оркестратор **предупреждает** в отчёте и на шаге сохранения («перед публикацией получите разрешение автора или найдите лицензию»), но сохранение не блокирует. Публикация на площадке — решение человека; плашка «Перевод» со ссылкой на оригинал и автора обязательна на любой площадке.

## Чек-лист перед выдачей готового перевода

- [ ] **Машинная сверка без блокирующих кодов** (`check_translation_fidelity`): лид на месте, заголовки по уровням, код без изменений, картинки с теми же URL и порядком, таблицы, авторские сноски, пометки «Прим. перев.».
- [ ] **Предупреждения сверки разобраны** проверяльщиком: абзацы, ссылки, числа — либо дефект исправлен, либо названа легитимная причина (дата, единица, якорь).
- [ ] **Порядок блоков** совпадает с оригиналом; тип блока не менялся.
- [ ] Названия продуктов и технологий — по «Общей таблице терминов» (`translation-glossary.md`), активным словарям и брифингу (если был); один термин — одно написание.
- [ ] Кавычки — «ёлочки»; длинное тире — только там, где em-dash стоял в оригинале; плотность не выше потолка редстандарта.
- [ ] **В оригинале нет тире → в переводе ноль длинных тире** (безусловно; машинная сверка без `EM_DASH_ADDED`).
- [ ] Числа, единицы, валюты, даты — по разделу «Числа и единицы измерения»; относительные даты — с годом из даты оригинала.
- [ ] Пояснения — только сносками «Прим. перев.» на первых упоминаниях, нумерация после авторских; в прозе нет инлайн-заметок, описаний в скобках и «русский термин (english original)».
- [ ] Аббревиатуры расшифрованы один раз, при первом упоминании.
- [ ] Голос автора сохранён: лицо, число, род; «мы» автора не стало «мы» публикатора.
- [ ] Буква «ё» — последовательно.
- [ ] Нет пропущенных и добавленных предложений; галлюцинаций 0.
- [ ] Блок атрибуции по канону; frontmatter по канону; `rights` заполнено (или `unknown` с предупреждением).
- [ ] Маркеры `EDITOR_RESHAPE` / `MISSING_FOOTNOTE` / `FEEDBACK-UP` разобраны оркестратором, в тексте их нет.
